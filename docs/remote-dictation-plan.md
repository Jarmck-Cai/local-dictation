# 远程窗口听写输入：隔离调查计划

## 范围与状态

本分支从 Beta 1 提交 `97d8c08bcb02d6763b324f4e90c5a64a911d7793` 分出，独立于会议功能后续修改。第一阶段只完成源码调查与验证计划，不修改生产输入算法。

目标场景：本机 Windows 运行听写，焦点位于远程控制窗口，希望正文进入远端当前编辑位置。用户现已在远端记事本复现自动输入出现问号，正文和普通复制正常（详见第三阶段）；开发者尚未进行受控固定文本发布对照，仍不能确定根因或承诺通用兼容。

用户已确认使用 Windows 远程桌面（RDP），远端也是 Windows。版本、窗口/全屏模式、键盘映射和剪贴板重定向设置随后按真实复现确认。

## 已核对的源码事实

- `desktop/src-tauri/src/clipboard.rs` 的 `paste_automatic_windows` 调用 `protected_paste::run_with_preflight`，复用受保护的剪贴板事务和键盘预检。
- `desktop/src-tauri/src/manual_paste.rs` 的 `send_paste_chord` 支持 Ctrl+V、Ctrl+Shift+V、Shift+Insert，通过 Enigo 注入；当前没有远端系统专用快捷键选择。Windows 本机按键释放观察与注入前快速复查均为现有保护。
- `desktop/src-tauri/src/protected_paste_windows.rs` 发布延迟渲染的 Unicode 文本；注入开始后收到 `WM_RENDERFORMAT` 才记录消费者读取。发布完成后重新取得剪贴板序列号，注入前同时验证序列号和所有权。
- `desktop/src-tauri/src/protected_paste_policy.rs` 的观察上限为 3 秒，读取后安静 150 毫秒即可进入结算。结算根据许可、取消状态和复制偏好恢复快照、保留结果或保留新复制。
- `desktop/src-tauri/src/protected_paste.rs` 明确说明：观察到读取不能证明目标已经插入文字。现有计时结果也保留此区别。
- `clipboard.rs` 的 `validate_paste_method` 明确拒绝 Direct 和 ExternalScript，不能把现有内部入口视为已支持的远程输入方案。

## 待验证的候选解释

这些是源码支持的调查方向，不是实测结论：

1. 远控客户端可能在本机读取剪贴板并异步同步到远端。本机读取回执无法表明远端已接收、应用已读取或插入；恢复时序和同步时序可能存在交互。
2. 粘贴组合键可能被本机、远控客户端或远端拦截。若本机 Windows 连接远端 macOS，还需核对 Ctrl 到 Command 的映射策略。
3. 剪贴板重定向可能未启用、仅单向启用或不接受延迟渲染发布，需要依据具体软件的官方协议/设置说明核实。
4. 按键状态预检、焦点变化或远控特殊键处理可能在注入前拒绝输入，需先区分错误反馈和无提示未落字。

## 下一阶段路线

取得软件与远端系统信息后，先查对应官方说明，再选择最小复现路径。使用固定合成文本，分别区分剪贴板传播、远端手动粘贴、自动组合键转发与正文最终落字；每项结果记录环境、观察范围和未证实部分。实际远控连接、系统剪贴板读写、发键和听写录音不属于本阶段已执行事项。

实现优先复用 `protected_paste_policy::Provider` 事务接口、`manual_paste_keyboard::Keyboard` 注入接口及现有输出协调许可。确有需要时在这些边界增加明确的远控策略，不通过取消所有权校验、覆盖并发复制、增加盲目重试或无限等待来获得表面成功。仅在证据明确后决定是否需要应用配置、快捷键映射或新的投递适配器。

## 第二阶段执行顺序

本阶段先在现有 Win32 发布合成适配器内增加独立的 RDP 场景（`python scripts/check-win32-publication.py --rdp`），继续逐字提取生产发布、租约、渲染、观察和结算方法。模型将格式列表到达、正文请求、本地预读和远端编辑器消费分开，使用虚拟时钟，绝不接触系统剪贴板或键盘。

- [x] 对照微软协议核实剪贴板与键盘链路，记录官方事实与工程推断。
- [x] 分别复现格式列表迟到、读后远端尚未消费、发键前预读、发键前短暂占用；同时覆盖普通本机输入、取消、并发新复制、恢复和一次注入。
- [x] 运行既有离线回归，记录每个断言的可证明范围，不把模型中安排的时序当作真实 RDP 行为。
- [ ] 在已识别的远端空白记事本使用固定合成文本区分剪贴板传播、手动粘贴、自动组合键与实际落字；现场未可用时保留此步骤，不凭合成模型挑选生产修复。
- [ ] 只有现场证据与离线最小复现指向相同边界时才修改该边界，再执行相关回归与复核；不改会议代码、版本、发布或安装。

候选原因的优先调查顺序（不是根因结论）：

1. 格式列表未到远端时组合键已经到达：模型应出现正文未被请求或旧内容被粘贴；本地延迟渲染并不能提供“远端格式列表就绪”信号。
2. 本机同步消费者提前读取：一次延迟渲染已被兑现，后续同格式读取不再通知临时所有者；应出现远端可落字但本机回执为未确认，或本机回执早于远端落字。
3. 同步客户端短暂持有本机剪贴板：`OpenClipboard` 立即失败，现有发键前租约检查退出，组合键次数应为零。
4. 按键转发、焦点与权限：剪贴板传播和远端手动粘贴可用，自动组合键没有触发远端读取。现有 Enigo 0.6.1 已为虚拟键填写扫描码，不能仅因 RDP 线上使用扫描码就认定要替换注入 API。

## 已完成的合成结果

`--rdp` 使用真实 `WinClipboard` 的发布、发键前检查、渲染、观察和结算方法，以及生产 `manual_paste_keyboard::inject_if_released` / `send_once`。Win32 API、窗口消息和网络端点由合成适配器代替；不会启动应用、连接远端、读写系统剪贴板或发键。键盘状态查询在该适配器中固定为全部松开，原生键状态来源由独立检查覆盖。

模型边界：虚拟 `sleep` 只推进时钟；取消、新复制、格式就绪及远端请求/消费在下一次 `pump` 或显式 `redirect_tick` 批量处理，不是完整并发调度器。例如安排在 80 ms 的请求实际在 100 ms 的组合键保持结束后服务，表中毫秒数是合成事件安排，不是实测延迟。当前场景不覆盖保持期间的所有交错；预读只兑现本地延迟数据，不模拟 CLIPRDR 缓存/失效策略；窗口销毁只清除合成上下文，不验证原生 `DestroyWindow` / `WM_RENDERALLFORMATS`。独立只读复核已确认这些证明边界、默认 20 项断言未削弱，以及显式红灯与修复验收的区别。

| 指定的合成时序 | 现有生产逻辑的结果 | 可推导范围 |
| --- | --- | --- |
| 远端格式已就绪，正文请求在 80 ms 或 1200 ms 后到达。 | 当前正文进入合成编辑器；一次组合键，本地快照恢复。 | 现有 3 秒观察窗能处理这些请求；不能证明真实 RDP 延迟。 |
| 组合键先到，40 ms 后格式列表才到。 | 合成远端使用旧内容，本机无读取回执；不会自动重贴。 | 模型中发键前远端尚未就绪是可失败边界；不能据此认定现场就是此时序。 |
| 本地取数后，合成远端延后 1200 ms 消费响应。 | 本地报告读取、恢复快照时远端尚未落字；已经复制进响应的正文仍可随后送达。 | 本地恢复不必然破坏已经复制的响应；读后统一加延迟缺少因果证据。 |
| 本地消费者在发键前预读正文，随后远端请求。 | 合成远端得到当前正文；本机没有第二次渲染回执，返回未确认。 | 未确认不等于一定没落字，自动重贴可能重复。 |
| 同步消费者在发键前短暂占用本机剪贴板 40 ms。 | 发键前检查返回忙；零次组合键，随后恢复快照。 | 存在可合成复现的发键前退出边界；是否属于现场原因仍须取得对应错误证据。 |
| 新复制发生在等待远端请求期间。 | 新复制优先，不恢复旧快照，不追加组合键，复制偏好亦不能覆盖。 | 保留原有并发复制保护。 |
| 取消发生在请求前或本地响应后。 | 恢复快照、返回取消、不追加组合键；已复制的远端响应仍可能随后落字。 | 本地取消无法撤回已经交给远端的编辑。 |
| 正文请求直到 3200 ms 才到。 | 3 秒截止后已恢复快照；过晚请求只能读到恢复后的内容，零次重贴。 | 有界借用无法承诺任意慢链路；延长固定期限也不提供远端确认。 |

### 无剪贴板的原生内存检查

`python scripts/check-protected-paste.py --native-text-memory --windows-rlib <已构建的windows-0.61.3.rlib>` 复用生产 `text_memory` / `MemoryLock` / `Global` 代码，只分配本进程内存并转换固定合成字符串，不创建窗口、不调用剪贴板或按键 API。

已执行结果：原保护策略 29 项通过，Win32 类型检查通过；5 个固定样本的生产 UTF-16 内存（含终止零、零初始化余量）与预期逐单元一致，UTF-8 转换逐字节一致，包含中文、中英混合、表情/非 BMP、换行与路径。强制将 `轻述远程输入测试 RDP 0123` 转为 CP1252 时，中文恰为 8 个问号，英文/数字保留，API 报告使用替代字符。

微软 [WideCharToMultiByte 文档](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-widechartomultibyte) 说明 UTF-16 转为无法表达全部字符的非 Unicode 代码页会丢失数据。[标准剪贴板格式](https://learn.microsoft.com/en-us/windows/win32/dataxchg/standard-clipboard-formats) 及 [格式合成规则](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats) 区分 Unicode、ANSI、OEM 与区域设置转换。上述结果证明生产缓冲区构造在这些输入上正确，以及有损转换可以产生相似症状；**不证明用户现场实际请求了 CF_TEXT、使用 CP1252，或具体哪一端做了转换**。

曾准备通过新建不可交互窗口站的独立空剪贴板验证真实格式请求顺序，但命名创建返回 Windows 错误 5，系统命名且要求新建返回 183。均在创建处终止，没有任何剪贴板调用；未提升权限、未复用既有窗口站，临时源码和日志仅本机归档。不能把这次不可用诊断记为真实剪贴板往返通过。

### 手动发布对照：两种模式均正常

构建命令：`python scripts/check-protected-paste.py --build-manual-rdp-probe outputs/manual-rdp-text-probe.exe --windows-rlib <已构建的windows-0.61.3.rlib>`。此命令只编译，不写剪贴板。生成程序不带参数或参数不精确匹配时，在所有原生 API 之前退出 2；该无副作用门禁已执行验证。

该诊断需先取得用户对具体测试时间窗与替换当前剪贴板的明确同意，再单次运行以下模式。本轮用户已明确允许两次各 20 秒，并确认远端空白记事本就绪；两次许可已经用于下列测试，不扩大为后续自动发键许可。它不备份或读取未知原内容，固定正文为 `轻述远程输入测试 RDP 0123`，结算目标为固定基线 `QINGSHU_TEST_CLIPBOARD_BASE_0123`。不能据此承诺保留测试前原剪贴板；新复制仍按生产的所有权/序列校验优先保留。

- `--manual-rdp-delayed`：复用生产发布/租约检查/延迟渲染/观察/结算，正文在本机消费者请求时提供。
- `--manual-rdp-materialized`：在相同发布后，另在自身剪贴板锁下调用生产 `render(..., false)`，在用户粘贴前准备 Unicode 正文；三个隐私标记不变。

两个模式均保留最多 20 秒的明确诊断窗口，由用户在已准备的远端空白记事本手动按 Ctrl+V。诊断不发出任何按键、不录音、不调用模型、不读取原剪贴板正文；分配逻辑从生产 `prepare` 的写入前部分提取，实际备份/读取部分由固定合成基线替代。20 秒只是手动操作的诊断窗口，**不是生产延迟修复**；程序结算或观察到本地读取都不表示远端正确落字，结果必须由用户确认。

该对照只区分延迟提供与提前物化的行为；不能验证正式自动按键时机。对照若两者都正常，继续调查自动时序和按键状态；若仅延迟模式异常，继续定位按需提供/格式请求边界；若两者均异常，则继续与普通复制的标记和格式差异对照。不得直接把任一结果扩大成已修复，正式算法当前未改。

本轮已执行：

- 延迟模式：本机观察到延迟渲染读取，20 秒后结算请求完成，程序退出 0。
- 提前物化模式：20 秒窗口内检测到来源/序列变化，按保护逻辑停止并保留新内容，程序以 `probe_new_copy_preserved` 退出 1；没有读取变化后的正文或覆盖它。这个退出码不等于远端文字传输失败。
- 用户确认两轮均显示固定正文 `轻述远程输入测试 RDP 0123`，没有问号，用户观察无差异。

因此，现有证据不支持“延迟渲染在该 RDP 环境必然损坏中文”或“仅由系统编码设置导致”。已验证的差别仍是正常人工粘贴与正式自动流程；手动对照的 20 秒稳定发布窗口没有复现自动流程的快捷键、3 秒截止与读取后 150 ms 结算。下一步优先区分录音触发快捷键残留、自动粘贴组合键与读取/恢复时序，而不是立即更换字符编码或以延长等待作为修复。

独立只读复核无阻断问题。准备函数的前半部分通过文本锚点提取，不是对未来调用图的安全证明；生产 `prepare` 或辅助函数改变后需重新审查。构建会在输出目录保留生成源码以及生产文件、策略、展开探针和二进制摘要，方便核对实际测试版本。固定基线只是结算请求，生产恢复失败时可能回退保留测试正文，不能宣称已核验恢复成功。

## 第四阶段：补贴复现与恢复策略对照

用户补充：在 RDP 编辑器使用“补贴最近结果”（默认 Ctrl+Shift+F9）也出现问号，重复两次；随后普通 Ctrl+V 仍得到此前复制的内容。只记录中文损坏、ASCII 保留及剪贴板恢复这一现象，不保存用户本次日常正文或其中的文件名。补贴路径不录音、不重新识别，因此录音或识别不是这次补贴异常的产生边界；它仍复用临时剪贴板与粘贴组合键，尚不能排除它自己的按键释放或客户端行为。

用户还观察到 Wispr Flow 在同类 RDP 场景能输入转录，随后此前复制内容被转录替代。这只是该次外部产品的可见行为，不能据此反推其闭源算法，也不是用户已同意轻述改变剪贴板恢复策略。

当前候选优先级：

1. 读取后的恢复/格式列表更新与远端消费发生交互；对照应只改变 `copy_result`，保留相同正文、组合键和观察条件。
2. 发布后尚未同步到远端时组合键已经到达；保留正文可能使后续手动粘贴可用，但不能因此把一次自动失败当成成功。
3. 合成组合键或按键状态与远端客户端交互；固定文本手动粘贴正常，不能证明自动注入的同一组合键也正常。
4. 快照读取或来源格式差异；目前固定探针故意跳过未知原剪贴板的备份，不能验证正式备份的所有副作用。

### 已执行的单次自动恢复/保留对照

`check-protected-paste.py --build-automatic-rdp-probe <输出exe> --windows-rlib <windows-0.61.3.rlib> --enigo-rlib <enigo-0.6.1.rlib>` 仅编译，原生构建检查已通过，保护策略 29 项通过；原手动探针构建仍通过。无参和零 PID 门禁均在任何原生 API 前退出 2，已执行核对。

实际模式要求分别明确允许在现有、已准备的远端记事本自动输入一次固定正文；之前两次手动测试授权不包含此行为。每个模式只允许一次 Ctrl+V，没有自动重试、Return、录音或模型调用：

- `--automatic-rdp-restore <pid>`：生产读取/结算策略，结算为固定合成基线。
- `--automatic-rdp-retain <pid>`：相同策略，仅把 `copy_result` 设为 true，保留固定测试正文。

目标必须是系统 `System32/mstsc.exe`，程序只读核对进程路径；5 秒倒计时后再次校验，前台窗口句柄和 PID 必须保持，变化则取消。复用真实 `keyboard_state_windows` 的 prepare/fast_check、真实单次按键控制器和从生产提取的 Enigo 适配器；每次按下前再查前台窗口，V 的第二次按下在调用 OS 前硬拒绝，释放始终清理。探针没有配置任何快捷键，绑定掩码为零，但物理按下、未知基线与观察代次保护不放宽。

该对照跳过未知原剪贴板正文的备份/读取，以固定基线替代；发布、观察、3 秒截止、读取后 150 ms 结算、新复制优先及取消使用生产实现。用户必须把光标留在已准备的远端编辑器，程序只验证本机客户端窗口，不能证明远端内部控件身份。它没有正式应用的完整备份、已有观察器生命周期及通知 UI，所以结果仍需限定证明范围。

若保留模式可用而恢复模式不可用，才进一步核对恢复边界；若两者均失败，恢复不是充分解释；若两者均成功，继续查正式备份、按键触发与实际配置差异。此处是诊断变量，不是已批准或已实现的 RDP 兼容策略，生产算法仍未改。

独立只读复核无阻断问题，核对生成源码、二进制、策略与键盘模块摘要一致。边界必须保留：前台/PID 检查与发键不是原子操作；前台变化后仍清理已尝试按键的释放；新复制优先保证结算不覆盖新内容，不能消除最后租约校验至发键间的瞬时复制竞态。对照差异只能支持继续定位结算/重发布相关路径，不能证明具体代码页或外部产品实现。

用户随后明确允许两轮自动对照并确认远端记事本光标就绪；本轮许可已消费。旧版固定文本探针分别执行 restore / retain，每轮日志均为一次 V 按下尝试、焦点未变、本机观察到读取、程序结算退出 0。用户确认两轮均为中文问号、`RDP 0123` 保留。因此，**保留结果并非该现场的充分修复**，不能从 Wispr 的可见行为直接选择保留策略。

旧程序、生成源码及摘要保留在本机独立产物中，不被后续构建覆盖。手动两轮因采用相同正文，无法完全排除旧缓存同文命中；此前“手动正常”应限定为用户看到了该字符串，不能据此严称已证明每次新发布均正确到达。后续对照增加唯一的案例编号。

## 第五阶段：合成按键表示对照（均未改善）

在相同生产事务、固定基线恢复、相同 Ctrl+V 组合键及单次保护下，仅比较虚拟键注入与扫描码注入。分别使用固定编号 `轻述远程输入测试 RDP V1` 与 `轻述远程输入测试 RDP S1`，以识别本轮发布，避免与旧缓存混同；编号本身不是编码或网络性能测量。

新诊断产物与上一轮隔离。`--automatic-rdp-scancode <pid>` 在捕获的目标窗口线程输入布局下调用 [MapVirtualKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mapvirtualkeyexw)，提前准备 Ctrl/V 的扫描码并在释放时复用；转发使用 Enigo `raw`。另一路仍使用原生产 Enigo 虚拟键适配器。所有目标身份、焦点、物理键/未知基线、取消、唯一 V 按下与结算保护保持。

已完成新探针构建/类型检查，保护策略 29 项通过，无参及零 PID 门禁均在原生调用前退出 2。尚未运行有效目标模式，需另行取得两轮具体测试窗口许可。正式应用代码未改；扫描码若有效，只能支持该输入表示的兼容性差异，不能反推客户端内部字符转换实现。

独立只读复核无当前 Ctrl/V 场景的阻断问题。适配器缓存了扫描码，但 Enigo `raw` 内部仍在当前前台布局中反向映射 VK/扩展标志，因此不能宣称整个释放链不依赖布局，也不能把本次非扩展 Ctrl/V 结论外推到任意扩展键。必须核对实际收到的 `V1/S1`，重复测试应使用新编号。

用户明确允许本轮两次自动输入并确认远端记事本就绪后，执行 V1 与 S1。每轮日志均为一次 V 按下尝试、焦点未变、本机读取已观察到、copy=false、结算退出 0。用户实际反馈分别为中文问号加 `RDP V1`、中文问号加 `RDP S1`。编号正确说明是本轮正文；**改用扫描码也不是充分修复**。本轮两次许可已消费，正式输入适配器未修改。

## 第六阶段：直接 Unicode 文本对照（U1 成功）

新增 `--automatic-rdp-unicode <pid>`，固定 BMP 文本为 `轻述远程输入测试 RDP U1`。与前述目标身份、5 秒倒计时和前台检查相同，先执行真实键状态 prepare/fast_check，末次复查目标后，只调用一次 Enigo Windows `text()`，在任何 `WinClipboard`/固定剪贴板对象构造前返回。该分支不使用 Ctrl+V、不读写剪贴板、不包含 Return/Tab/控制字符、不录音、不调用模型，失败不重试。

已核对本机固定 Enigo 0.6.1 Windows 实现：本样本构造一组 `KEYEVENTF_UNICODE` 按下/释放事件，只调用一次 SendInput，只有完整事件数被接受才返回 Ok。其换行/Tab处理及非 BMP 释放 TODO 不属于此固定 BMP 样本范围，不能外推支持情况。微软分别定义 [KEYBDINPUT Unicode 模式](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput) 与 [RDP Unicode 键盘事件](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/551b9903-8fb9-4d00-b3ac-a187431efb86)；协议存在该类型不等于已验证当前客户端一定正确转发。

新产物独立于前两轮，已构建/类型检查通过，保护策略 29 项通过；独立只读复核无当前样本阻断问题，无参及零 PID 均在原生输入前退出 2。尚未运行有效模式，正在请求新的单次测试窗口授权。OS 接受全部事件不证明远端落字；最终焦点检查至提交仍非原子，批次进入 OS 后不能中途撤回，部分失败不可自动重试。正式应用和已禁用的 Direct 设置均未改变。

用户随后明确允许本轮单次 U1 输入并确认远端记事本光标就绪。实际程序日志为单个 Unicode 批次、OS 接受全部事件、剪贴板 API 调用为零、退出 0；用户确认看到正常中文及 `RDP U1`。本次许可已经消费。该结果验证了当前 MSTSC/远端记事本对这个固定 BMP 样本的直接 Unicode 路径，不证明所有应用、非 BMP、长文本或正式客户端完整路由已验收。

当前可工程定位的边界为“本环境中的自动剪贴板投递损坏中文，直接 Unicode 输入可用”；没有捕获到具体哪一端或哪次 CF_TEXT/CF_UNICODETEXT 转换，不能将 CP1252 或特定闭源逻辑认定为根因。

## 第七阶段：外部方案调研后再定实现

用户要求安排一个独立子代理研究微软资料及开源方案，再权衡实现。暂不写正式输入算法；保留 U1 为已有实测支持的候选，不提前认定最终方案。研究需比较剪贴板格式/恢复策略、Unicode 直接输入、检测前台 RDP 客户端与运行于远端会话的区别、取消/单次提交/非 BMP/长文本/复制偏好等边界，并区分协议约定、开源实现与本机实测。

### 调研结论与候选排序

独立调研已整理微软协议/API 和 FreeRDP、Handy、OpenWhispr、AutoHotkey、当前 Enigo 固定版本的源码；详细笔记仅保留本机。源码阅读不能代替当前环境的兼容验收，也没有提供当前 MSTSC 内部发生哪次转换的证据。

- [MS-RDPECLIP 的交互流程](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpeclip/9a784d09-bf53-4362-995d-a20d0eb5f074) 将格式列表、按需正文传输、应用取数分为多个阶段。格式回执、本地延迟渲染读取均不是远端落字回执；文件流锁不能作为普通文本的冻结或落字确认。
- [Windows 的格式合成](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats#synthesized-clipboard-formats) 允许 Unicode 与 ANSI/OEM 文本转换。只提供 Unicode 不代表消费者不能请求合成格式；owner 收到 Unicode 渲染请求也不能唯一确定消费者原始请求格式。现场仍缺实际格式/响应编码证据，不认定 CF_TEXT、CP1252 或线程 locale 为根因。
- [FreeRDP Windows 实现](https://github.com/FreeRDP/FreeRDP/blob/f0f03eb0290d0ff600696763edf44ea2e37a455b/client/Windows/wf_cliprdr.c#L1218-L1279) 按请求的格式 ID 从系统剪贴板取数，可借鉴其协议分层；不能把它当作闭源 MSTSC 的实现证明。其他文本工具的固定等待、保留剪贴板或重试策略也不能覆盖本分支已经失败的单变量对照。
- [当前 Enigo 0.6.1 源码](https://github.com/enigo-rs/enigo/blob/b297a14e807abdf818b7809a70b445ade4fc5897/src/win/win_impl.rs#L276-L298) 的 LF/Tab 会排入实体 Return/Tab 后再排 Unicode 字符；[非 BMP 释放](https://github.com/enigo-rs/enigo/blob/b297a14e807abdf818b7809a70b445ade4fc5897/src/win/win_impl.rs#L475-L504) 使用首个 UTF-16 单元。本机依赖 commit 与源码已复核。U1 不包含这些字符，因此不能直接放开该入口处理任意正文。
- [MsTscAx 手动剪贴板同步接口](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpclipboard) 确实存在，但未找到外部应用附着任意系统 MSTSC 取得该控制器的受支持方式；同步成功也没有编辑器落字语义。不要笼统宣称 RDP 没有同步 API。

工程建议排序为：优先验证已识别系统 MSTSC 的有界 Unicode 适配器；剪贴板修正继续作为需额外格式/时序证据的路线；自有客户端或远端辅助组件会引入部署与维护，暂不进入本轮。该排序基于 U1 正向实测和本轮成本，不是用户已禁止远端组件，也不是 Unicode 已完成验收。

若继续实现，须保留真实键状态、取消、输出时前台身份复查、一次提交与新复制优先；默认直接输入不碰剪贴板，显式复制偏好另行安全结算。离线先核对 UTF-16、控制字符、长度/溢出、部分接受与焦点变化；不以返回错误推定零输入，不自动重贴。日志区分“OS 接受输入”与“剪贴板读取”，两者均不能称远端已确认。正式算法、配置、安装版及已禁用的 Direct 设置在本调研阶段仍未改动。

## 第八阶段：用户批准的 MSTSC Unicode 适配

用户随后明确批准实现 MSTSC Unicode 适配、保留本机原行为，完成离线检查后再由用户验证远端。这是开发授权，不将以前已经消费的输入许可复用为本轮实际发键许可。

实现位于 `rdp_input.rs` / `rdp_input_windows.rs`，在现有输入互斥锁和按键释放等待之后识别前台 PID、持有查询进程句柄，并将完整路径与 `GetSystemDirectoryW` 得到的系统目录比较。仅匹配系统 MSTSC；前台或身份不可确认时在提交前拒绝，不使用标题、账户或远端编辑器正文。普通本机仍走原受保护剪贴板；不启用 Direct 或脚本设置。

正式字符事件不调用 Enigo `text()`：正文先沿用原有单行规范化，底层拒绝控制字符和非普通空格的空白，以每个 UTF-16 单元的对称按下/释放构造一次 `KEYEVENTF_UNICODE` 数组。首版限制 4096 个 UTF-16 单元；超过上限先拒绝、保留历史供明确复制，不拆批、不自动换机制。最终复查现有键状态 token、前台 HWND/PID 与取消后仅提交一次；系统接受事件数与远端实际落字仍分开。

自动输入与手动补贴均接入；手动成功按“输入已发起但无读取回执”呈现，不受自动复制偏好影响。默认 Unicode 完全不创建剪贴板对象。显式复制偏好先用已有尽力快照/隐私标记分配资源，释放剪贴板锁后准备键盘；完整提交后在同一锁内比较原 owner、sequence 与取消，再决定写入或保留新复制。写入失败尽力恢复原快照并报告“输入已提交但复制未完成”，不会重新输入。第一次 EmptyClipboard 本身失败时不再额外清空回滚。

验证先红后绿：真实自动编排用例从合成的 `???????? RDP T1` 失败转为 Unicode 正文，且无粘贴组合键/剪贴板发布；字符策略 10 项通过，实际原生 API 边界合成 17 项通过，原生模块全量类型检查通过。自动路由专项 76 项、发布/RDP 时序/复制租约 74 项、键状态 42 项、保护策略 29 项、快照 19 项及补贴多组回归通过。测试之间含共享策略断言，不能相加为互不重复的用例数，也不能冒充真实远端落字。

独立审查发现浮窗漏掉新增错误码、耗时状态缺翻译两项问题，均先用实际状态生产/消费与 i18next 回退测试复现，再修复并转绿。完整 Rust 单元测试在固定运行库环境中 678 通过、6 个原有忽略；首轮因独立测试目录缺少固定 DLL 而加载系统 ORT 1.17.1，导致两个会议缺失 VAD 的合成测试失败及退出时 panic。将已核对的 1.24.2 DLL 放入本任务独立测试目录后，两项及全套通过；没有修改会议代码或使用真实录音/模型。

U2 验收工具只编译并保存当前源码/二进制摘要，无参和零 PID 均在桌面 API 前退出 2。有效模式尚未执行；仍需新的具体固定文本/远端记事本测试窗口。它复用正式 Unicode 和键状态边界，默认不访问剪贴板；没有安装候选应用，也未验证正式应用完整快捷键链路、全部远端控件/IME/长正文或其他客户端。源代码提交不等于安装或已发布修复。

## 第九阶段：U2 现场反馈与扩展字符边界

用户明确允许一次 U2 后，又分别明确要求两次重测，共执行三次相同冻结工具；每次重新核对二进制摘要及唯一系统 MSTSC 进程，只提交一批，OS 接受全部事件，剪贴板 API 调用为零，没有 Return、录音或模型。三次许可均已消费，不自动重跑。安装版未变。

首次反馈不能确认完整编号，因此未据此定位字符类别。后续用户粘贴并提供截图确认：`轻述远程输入测试 RDP U2` 及笑脸显示正常；最后的 U+20000 扩展汉字呈异常占位符。随后用户手动复制回来的笑脸仍正常，扩展汉字在回复中表现为两个低代理单元，未保持预期的 D840 DC00 配对。这不足以用单纯字体缺字解释完整往返，但仍未证明损坏发生于自动输入、远端编辑器、复制回传或回复的哪一个阶段。不能认定所有非 BMP 都失败，也不将整个 U2 记为完整通过。

新增针对 U+20000 的实际原生 INPUT 构造诊断：在替换桌面 API 的边界中，生产事件确为 D840-down、D840-up、DC00-down、DC00-up，一次提交且无剪贴板调用；纯策略 10 项、原生合成 18 项通过。它证明传给 API 的构造，不证明真实 OS、MSTSC 或远端已正确处理。保留此前已实际执行的 U2 产物，不以新构建覆盖现场版本。

下一项人工对照为固定 `RDP M3 😀 𠀀 END`：由用户从本对话手动复制到相同远端记事本，再将该段复制回复。当前仅提出对照，尚无结果，不运行新工具或读系统剪贴板。该对照用于进一步区分自动字符路径与共同的显示/复制回传边界；若回传仍损坏，不能单靠它证明输入原文已经损坏。正式事件顺序和字符支持策略暂不凭症状修改。

## 第十阶段：M3 完整往返与输入前兼容保护

用户完成 M3 人工对照并返回完整 `RDP M3 😀 𠀀 END`，明确远端与复制回本机都清晰。因此，普通剪贴板往返和该远端显示能力能够保留 U+20000，问题进一步收窄到当前自动 Unicode 路径的扩展字符处理；尚不能确定是 Win32 输入处理、客户端转发还是远端事件消费的哪一层。没有据此改变按下/释放顺序或调用次数，也不声称已修复扩展汉字传输。

首版新增临时兼容范围：MSTSC 自动/补贴正文只接受 U+0000..U+1FFFF 中符合既有单行/控制字符/长度规则的字符。只要整段含更高平面字符，就在任何键盘准备、复制准备或提交前整段拒绝，最近转录中的原正文仍完整；通过专用提示让用户明确复制、手动粘贴。不是删除这些字符、截断正文、只送正常前缀，也不是一次提交失败后的自动补贴。本机原剪贴板路径、BMP 和 Plane 1 表情路径保持。这个上限是本项目依据现场反馈设置的兼容保护，不是 Windows/RDP 协议限制，也不代表范围内所有远端应用都已验收。

保护用例先红：原自动编排会将含失败字符的正文记为 UnicodeSubmitted；补贴的字符拒绝没有明确复制提示。修正后自动/补贴/本机/笑脸路由 80 项通过，纯策略 11 项、原生边界合成 19 项通过；拒绝用例含正常前缀、笑脸及扩展字符，核对零输入、零剪贴板操作和不自动回退。本机相同高平面正文仍走原路径，远端笑脸仍通过 Unicode。原生类型检查、错误浮窗/两种语言恢复提示通过；完整 Rust 679 通过、6 个原有忽略。独立范围复核无 must-fix。

当前构建工具改为 B1 固定中英/笑脸样本与 `--mstsc-unicode-b1` 标志，新产物另存；无参、零 PID、旧标志均退出 2，B1 有效模式未执行。旧 U2 实测程序/生成源码/摘要保留，不覆盖历史版本，也不再复用三次已消费授权。当前无需用户继续重复固定输入；安装候选后的完整应用路由仍由后续集成验收处理。
