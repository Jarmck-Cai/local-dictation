# 远程窗口听写输入：隔离调查计划

## 范围与状态

本分支从 Beta 1 提交 `97d8c08bcb02d6763b324f4e90c5a64a911d7793` 分出，独立于会议功能后续修改。第一阶段只完成源码调查与验证计划，不修改生产输入算法。

目标场景：本机 Windows 运行听写，焦点位于远程控制窗口，希望正文进入远端当前编辑位置。用户现已在远端记事本复现自动输入出现问号，正文和普通复制正常（详见第三阶段）；开发者尚未进行受控固定文本发布对照，仍不能确定根因或承诺通用兼容。

用户已确认使用 Windows 远程桌面（RDP），远端也是 Windows。版本、窗口/全屏模式、键盘映射和剪贴板重定向设置随后按真实复现确认。

## 已核对的源码事实

- `desktop/src-tauri/src/clipboard.rs` 的 `paste_automatic_windows` 调用 `protected_paste::run_with_preflight`，复用受保护的剪贴板事务和键盘预检。
- `desktop/src-tauri/src/manual_paste.rs` 的 `send_paste_chord` 支持 Ctrl+V、Ctrl+Shift+V、Shift+Insert，通过 Enigo 注入；当前没有远端系统专用快捷键选择。Windows 本机按键释放观察与注入前快速复查均为现有保护。
- `desktop/src-tauri/src/protected_paste_windows.rs` 发布延迟渲染的 Unicode 文本；注入开始后收到 `WM_RENDERFORMAT` 才记录消费者读取。发布完成后重新取得剪贴板序列号，注入前同时验证序列号和所有权。
- `desktop/src-tauri/src/protected_paste_policy.rs` 的观察上限为 3 秒，读取后安静 150 毫秒即可进入结算。结算根据许可、取消状态和复制偏好恢复快照、保留结果或保留新复制。
- `desktop/src-tauri/src/protected_paste.rs` 明确说明：观察到读取不能证明目标已经插入文字。现有计时结果也保留此区别。
- `clipboard.rs` 的 `validate_paste_method` 明确拒绝 Direct 和 ExternalScript，不能把现有内部入口视为已支持的远程输入方案。

## 待验证的候选解释

这些是源码支持的调查方向，不是实测结论：

1. 远控客户端可能在本机读取剪贴板并异步同步到远端。本机读取回执无法表明远端已接收、应用已读取或插入；恢复时序和同步时序可能存在交互。
2. 粘贴组合键可能被本机、远控客户端或远端拦截。若本机 Windows 连接远端 macOS，还需核对 Ctrl 到 Command 的映射策略。
3. 剪贴板重定向可能未启用、仅单向启用或不接受延迟渲染发布，需要依据具体软件的官方协议/设置说明核实。
4. 按键状态预检、焦点变化或远控特殊键处理可能在注入前拒绝输入，需先区分错误反馈和无提示未落字。

## 下一阶段路线

取得软件与远端系统信息后，先查对应官方说明，再选择最小复现路径。使用固定合成文本，分别区分剪贴板传播、远端手动粘贴、自动组合键转发与正文最终落字；每项结果记录环境、观察范围和未证实部分。实际远控连接、系统剪贴板读写、发键和听写录音不属于本阶段已执行事项。

实现优先复用 `protected_paste_policy::Provider` 事务接口、`manual_paste_keyboard::Keyboard` 注入接口及现有输出协调许可。确有需要时在这些边界增加明确的远控策略，不通过取消所有权校验、覆盖并发复制、增加盲目重试或无限等待来获得表面成功。仅在证据明确后决定是否需要应用配置、快捷键映射或新的投递适配器。

## 第二阶段执行顺序

本阶段先在现有 Win32 发布合成适配器内增加独立的 RDP 场景（`python scripts/check-win32-publication.py --rdp`），继续逐字提取生产发布、租约、渲染、观察和结算方法。模型将格式列表到达、正文请求、本地预读和远端编辑器消费分开，使用虚拟时钟，绝不接触系统剪贴板或键盘。

- [x] 对照微软协议核实剪贴板与键盘链路，记录官方事实与工程推断。
- [x] 分别复现格式列表迟到、读后远端尚未消费、发键前预读、发键前短暂占用；同时覆盖普通本机输入、取消、并发新复制、恢复和一次注入。
- [x] 运行既有离线回归，记录每个断言的可证明范围，不把模型中安排的时序当作真实 RDP 行为。
- [ ] 在已识别的远端空白记事本使用固定合成文本区分剪贴板传播、手动粘贴、自动组合键与实际落字；现场未可用时保留此步骤，不凭合成模型挑选生产修复。
- [ ] 只有现场证据与离线最小复现指向相同边界时才修改该边界，再执行相关回归与复核；不改会议代码、版本、发布或安装。

候选原因的优先调查顺序（不是根因结论）：

1. 格式列表未到远端时组合键已经到达：模型应出现正文未被请求或旧内容被粘贴；本地延迟渲染并不能提供“远端格式列表就绪”信号。
2. 本机同步消费者提前读取：一次延迟渲染已被兑现，后续同格式读取不再通知临时所有者；应出现远端可落字但本机回执为未确认，或本机回执早于远端落字。
3. 同步客户端短暂持有本机剪贴板：`OpenClipboard` 立即失败，现有发键前租约检查退出，组合键次数应为零。
4. 按键转发、焦点与权限：剪贴板传播和远端手动粘贴可用，自动组合键没有触发远端读取。现有 Enigo 0.6.1 已为虚拟键填写扫描码，不能仅因 RDP 线上使用扫描码就认定要替换注入 API。

## 已完成的合成结果

`--rdp` 使用真实 `WinClipboard` 的发布、发键前检查、渲染、观察和结算方法，以及生产 `manual_paste_keyboard::inject_if_released` / `send_once`。Win32 API、窗口消息和网络端点由合成适配器代替；不会启动应用、连接远端、读写系统剪贴板或发键。键盘状态查询在该适配器中固定为全部松开，原生键状态来源由独立检查覆盖。

模型边界：虚拟 `sleep` 只推进时钟；取消、新复制、格式就绪及远端请求/消费在下一次 `pump` 或显式 `redirect_tick` 批量处理，不是完整并发调度器。例如安排在 80 ms 的请求实际在 100 ms 的组合键保持结束后服务，表中毫秒数是合成事件安排，不是实测延迟。当前场景不覆盖保持期间的所有交错；预读只兑现本地延迟数据，不模拟 CLIPRDR 缓存/失效策略；窗口销毁只清除合成上下文，不验证原生 `DestroyWindow` / `WM_RENDERALLFORMATS`。独立只读复核已确认这些证明边界、默认 20 项断言未削弱，以及显式红灯与修复验收的区别。

| 指定的合成时序 | 现有生产逻辑的结果 | 可推导范围 |
| --- | --- | --- |
| 远端格式已就绪，正文请求在 80 ms 或 1200 ms 后到达。 | 当前正文进入合成编辑器；一次组合键，本地快照恢复。 | 现有 3 秒观察窗能处理这些请求；不能证明真实 RDP 延迟。 |
| 组合键先到，40 ms 后格式列表才到。 | 合成远端使用旧内容，本机无读取回执；不会自动重贴。 | 模型中发键前远端尚未就绪是可失败边界；不能据此认定现场就是此时序。 |
| 本地取数后，合成远端延后 1200 ms 消费响应。 | 本地报告读取、恢复快照时远端尚未落字；已经复制进响应的正文仍可随后送达。 | 本地恢复不必然破坏已经复制的响应；读后统一加延迟缺少因果证据。 |
| 本地消费者在发键前预读正文，随后远端请求。 | 合成远端得到当前正文；本机没有第二次渲染回执，返回未确认。 | 未确认不等于一定没落字，自动重贴可能重复。 |
| 同步消费者在发键前短暂占用本机剪贴板 40 ms。 | 发键前检查返回忙；零次组合键，随后恢复快照。 | 存在可合成复现的发键前退出边界；是否属于现场原因仍须取得对应错误证据。 |
| 新复制发生在等待远端请求期间。 | 新复制优先，不恢复旧快照，不追加组合键，复制偏好亦不能覆盖。 | 保留原有并发复制保护。 |
| 取消发生在请求前或本地响应后。 | 恢复快照、返回取消、不追加组合键；已复制的远端响应仍可能随后落字。 | 本地取消无法撤回已经交给远端的编辑。 |
| 正文请求直到 3200 ms 才到。 | 3 秒截止后已恢复快照；过晚请求只能读到恢复后的内容，零次重贴。 | 有界借用无法承诺任意慢链路；延长固定期限也不提供远端确认。 |

### 无剪贴板的原生内存检查

`python scripts/check-protected-paste.py --native-text-memory --windows-rlib <已构建的windows-0.61.3.rlib>` 复用生产 `text_memory` / `MemoryLock` / `Global` 代码，只分配本进程内存并转换固定合成字符串，不创建窗口、不调用剪贴板或按键 API。

已执行结果：原保护策略 29 项通过，Win32 类型检查通过；5 个固定样本的生产 UTF-16 内存（含终止零、零初始化余量）与预期逐单元一致，UTF-8 转换逐字节一致，包含中文、中英混合、表情/非 BMP、换行与路径。强制将 `轻述远程输入测试 RDP 0123` 转为 CP1252 时，中文恰为 8 个问号，英文/数字保留，API 报告使用替代字符。

微软 [WideCharToMultiByte 文档](https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-widechartomultibyte) 说明 UTF-16 转为无法表达全部字符的非 Unicode 代码页会丢失数据。[标准剪贴板格式](https://learn.microsoft.com/en-us/windows/win32/dataxchg/standard-clipboard-formats) 及 [格式合成规则](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats) 区分 Unicode、ANSI、OEM 与区域设置转换。上述结果证明生产缓冲区构造在这些输入上正确，以及有损转换可以产生相似症状；**不证明用户现场实际请求了 CF_TEXT、使用 CP1252，或具体哪一端做了转换**。

曾准备通过新建不可交互窗口站的独立空剪贴板验证真实格式请求顺序，但命名创建返回 Windows 错误 5，系统命名且要求新建返回 183。均在创建处终止，没有任何剪贴板调用；未提升权限、未复用既有窗口站，临时源码和日志仅本机归档。不能把这次不可用诊断记为真实剪贴板往返通过。

### 手动发布对照：两种模式均正常

## 第四阶段：补贴复现与恢复策略对照

用户补充：在 RDP 编辑器使用“补贴最近结果”（默认 Ctrl+Shift+F9）也出现问号，重复两次；随后普通 Ctrl+V 仍得到此前复制的内容。只记录中文损坏、ASCII 保留及剪贴板恢复这一现象，不保存用户本次日常正文或其中的文件名。补贴路径不录音、不重新识别，因此录音或识别不是这次补贴异常的产生边界；它仍复用临时剪贴板与粘贴组合键，尚不能排除它自己的按键释放或客户端行为。

用户还观察到 Wispr Flow 在同类 RDP 场景能输入转录，随后此前复制内容被转录替代。这只是该次外部产品的可见行为，不能据此反推其闭源算法，也不是用户已同意轻述改变剪贴板恢复策略。

当前候选优先级：

1. 读取后的恢复/格式列表更新与远端消费发生交互；对照应只改变 `copy_result`，保留相同正文、组合键和观察条件。
2. 发布后尚未同步到远端时组合键已经到达；保留正文可能使后续手动粘贴可用，但不能因此把一次自动失败当成成功。
3. 合成组合键或按键状态与远端客户端交互；固定文本手动粘贴正常，不能证明自动注入的同一组合键也正常。
4. 快照读取或来源格式差异；目前固定探针故意跳过未知原剪贴板的备份，不能验证正式备份的所有副作用。
